# RL and GNN scheduling: gap analysis reveals novel ground

No existing paper combines MaskablePPO with GraphSAGE for CPU process scheduling, soft priority-plus-aging rewards, dynamic action masking for variable process counts, and statistical evaluation across hundreds of seeded workloads. The literature spans three largely non-overlapping domains — OS/CPU scheduling, cluster/cloud job scheduling, and manufacturing job-shop scheduling — each of which addresses some but not all of these design choices. The landmark papers (DeepRM, Decima, RLScheduler) collectively establish that RL can beat classical heuristics, but all optimize aggregate efficiency metrics like average job completion time with no explicit fairness or priority mechanism, and none operate at the OS process-scheduling granularity. This survey identifies exactly what each major line of work does and does not do, enabling precise positioning of a project that brings graph-structured state representation, principled invalid-action handling, and anti-starvation reward design to the CPU scheduling problem.

## Classical RL schedulers use flat vectors and ignore process structure

The foundational deep RL scheduler, **DeepRM** (Mao et al., ACM HotNets 2016), represents cluster state as a 2D image of CPU and memory occupancy and uses REINFORCE policy gradient to select which job to run next ([Source](https://www.microsoft.com/en-us/research/publication/resource-management-deep-reinforcement-learning/)). It beat SJF and the Tetris heuristic under a wide range of loads on synthetic workloads, but its image-based state representation proved unscalable: later work explicitly notes that "DeepRM's state representation cannot handle realistic cluster workloads with continuous job arrivals." **RLScheduler** (Zhang et al., arXiv 2019/SC20) fixed this by switching to per-job feature vectors (submission time, requested processors, runtime estimate, memory) padded to 128 entries, applying a 3-layer MLP to each job independently (a kernel-based DNN), and training with **PPO** ([Source](https://ar5iv.labs.arxiv.org/html/1910.08925)). RLScheduler matches or exceeds state-of-the-art heuristics (SJF, WFP3, UNICEP, F1) across six real HPC workload traces with inference cost of 0.3 ms for 128 jobs, and generalizes to unseen traces with controlled degradation. However, it assumes homogeneous compute, caps observations at 128 jobs, uses no graph structure, has no action masking, and includes no explicit fairness or priority in its reward — all gaps directly addressed by the project under comparison.

For OS-level kernel scheduling, the most relevant published work is **STUN** (Lee, Jung, Jo; Applied Sciences MDPI 2022), which uses **tabular Q-learning** (not deep RL) to tune five Linux kernel scheduler policies and ten CFS parameters automatically, achieving 18.3% execution time improvement and 22.4% FPS improvement on a face detection workload ([Source](https://www.mdpi.com/2076-3417/12/14/7072)). Critically, STUN does not make per-process scheduling decisions — it is a global parameter optimizer, not a decision-making scheduler. Similarly, TuneAgent (arXiv 2025) applies LLM-guided RL to Linux kernel tuning, beating baselines by 5.6%, but again operates at the parameter level, not the process-dispatch level. The GitHub project RL-OS-Scheduling uses Q-learning to adapt MLFQ time quanta, which is closer in spirit to per-process scheduling but remains a student project without peer-reviewed evaluation or deep learning. **The gap is clear: no published, peer-reviewed paper uses deep RL to make per-timeslice, per-process scheduling decisions in a CPU simulator with process-level features (burst time, wait time, priority, arrival time).**

## Decima establishes GNN + RL for scheduling but at the wrong granularity

**Decima** (Mao et al., ACM SIGCOMM 2019) is the most influential paper combining GNNs with RL for scheduling, and it deserves detailed treatment ([Source](https://zilimeng.com/papers/decima-sigcomm19.pdf)). Decima represents Spark job DAGs as graphs — nodes are job stages, edges are dependencies — and uses a custom GNN with a distinctive two-transform aggregation (shown empirically to outperform single-transform GCN-style aggregation) to produce node, job, and global embeddings. A policy network then outputs (1) which stage to schedule and (2) how many Spark executors to assign. Evaluated on a **25-node Spark cluster** with TPC-H query mixes, Decima achieves at least **21% improvement in average JCT** over hand-tuned heuristics, and 45% improvement over the naive non-GNN variant, confirming that graph structure in the state representation carries significant signal ([Source](https://news.mit.edu/2019/decima-data-processing-0821)). Decima does use a limited form of action masking — previously scheduled nodes are masked to prevent re-selection — but this is far narrower than MaskablePPO-style systematic constraint enforcement for invalid actions.

Decima's limitations are well-documented. It "learns workload-specific policies whose effectiveness depends on whether broad test workload characteristics match the training workload," performing poorly when trained on an anti-skewed workload and tested on normal conditions ([Source](https://arxiv.org/html/2405.19131v1)). It does not support advance reservations, has no priority or fairness mechanism in its reward, and its GNN architecture is custom-built rather than using a standard inductive GNN like GraphSAGE. A 2024 follow-up (Hu et al., arXiv 2405.19131) distills Decima's policy into interpretable decision trees, finding that naive Decima "does not handle or adapt to edge cases effectively." Most importantly for the comparison at hand: Decima operates on Spark DAGs in a cluster, not on OS processes competing for a single CPU, and its graph nodes represent computational stages with resource requirements — not processes with priority, wait time, and burst-time attributes.

## GNNs for job-shop scheduling generalize across sizes but never use GraphSAGE

The manufacturing job-shop scheduling (JSSP) literature independently developed GNN + RL systems with sophisticated graph representations. **L2D (Learning to Dispatch, Zhang et al., NeurIPS 2020)** uses a disjunctive graph where nodes are operations and edges are either conjunctive (precedence) or disjunctive (machine contention), combined with a **Graph Isomorphism Network (GIN)** and **PPO** ([Source](https://nips.cc/virtual/2020/public/poster_11958dfee29b6709f48a9ba0387a2431.html)). The key design insight is that GIN's theoretical expressiveness (stronger than GCN for distinguishing graph structures) plus the disjunctive graph captures scheduling constraints that flat vectors cannot. L2D produces a "size-agnostic policy network" that generalizes to larger problem instances than those seen during training. **Geometric Deep RL for Dynamic DAG Scheduling** (Grinsztajn et al., arXiv 2020) extends this to dynamic DAG scheduling in HPC using **GCN + A2C**, achieving competitive performance with expert ASAP heuristics on Cholesky factorization, and demonstrating strong transfer to different problem sizes and resource counts ([Source](https://arxiv.org/html/2011.04333v1)).

A 2024 survey of GNN approaches to job-shop scheduling (arXiv 2406.14096) confirms that GCN, GIN, and GAT are the dominant architectures, with GraphSAGE absent from the scheduling literature entirely ([Source](https://arxiv.org/pdf/2406.14096)). The **GNN-RL HPC scheduler** (Adimora et al., SC24) is the most recent major work, using **Graph Attention Networks (GAT) + PPO** evaluated on 377,234 real ALCF supercomputer jobs, achieving **13.8–20.2% utilization improvement** and **15–50% throughput improvement** over the EASY-BF baseline, with 76% effectiveness at 50K concurrent jobs ([Source](https://sc24.supercomputing.org/proceedings/poster/poster_files/post137s2-file3.pdf)). GAT, like GraphSAGE, is inductive — it generalizes to graphs of variable size — which is described as "essential because the job queue changes at every scheduling step." The fact that GAT appears in recent work for exactly this inductive-generalization reason makes GraphSAGE, with its neighborhood-sampling aggregation mechanism originally designed for large dynamic graphs (Hamilton, Ying, Leskovec; NeurIPS 2017), a well-motivated but unexplored choice for the CPU scheduling domain ([Source](https://cs.stanford.edu/people/jure/pubs/graphsage-nips17.pdf)).

## Action masking has solid theory but no CPU scheduling applications

The theoretical foundation for action masking in policy gradient algorithms was established by **Huang & Ontañón (FLAIRS 2022 / arXiv 2020)** ([Source](https://ar5iv.labs.arxiv.org/html/2006.14171)). Their key result (Proposition 1) proves that replacing invalid-action logits with a large negative constant (e.g., −1×10⁸) before softmax produces **valid policy gradients for the masked policy** π'_θ, because the masking function is a state-dependent differentiable transformation. The alternative — penalizing invalid actions with a negative reward — fails at scale: on a 10×10 μRTS map, penalty-based methods require 3.43% of training time merely to achieve a first reward, versus 0.06% for masking, and penalty hyperparameter tuning proved intractable as action space grew. The canonical implementation is **MaskablePPO** in sb3-contrib, which applies the −∞ logit technique through a `use_masking` flag in `collect_rollouts()` and an `action_masks` parameter in `get_distribution()` ([Source](https://sb3-contrib.readthedocs.io/en/master/modules/ppo_mask.html)).

The most directly relevant applied paper is **Lassoued et al. (Expert Systems with Applications, 2026)**, which applies **Maskable PPO** — explicitly citing sb3-contrib — to **dynamic job-shop scheduling** under machine failures and stochastic arrivals ([Source](https://arxiv.org/html/2601.09293v1)). They represent state as Colored-Timed Petri Nets, mask invalid job-machine transitions via Petri net guard functions, and innovate a gradient-based masking variant (adding a penalty term λ_inv × Σπ_θ(a|s) for invalid actions) to help the agent internalize feasibility constraints. Their 100-run evaluation with 95% confidence intervals is the most rigorous statistical methodology found in any action-masking scheduler paper. Critically, this paper does not address CPU/OS process scheduling, uses no GNN for state representation, has no priority or fairness mechanism, and its training is problem-instance-specific — the agent does not generalize across problem sizes. The target project's use of MaskablePPO for CPU process scheduling (masking "empty" process slots when fewer than the maximum 8 processes are present) fills this gap with a more principled inductive approach via GraphSAGE.

## Priority-aware and fairness-aware RL reward design remains underdeveloped

The majority of RL schedulers — Decima, DeepRM, RLScheduler, L2D, and the MARL cluster scheduler (Zhao & Wu, arXiv 2021) — optimize a single efficiency metric (average JCT or makespan) with no explicit treatment of job priority or anti-starvation fairness ([Source](https://arxiv.org/html/2112.13354)). The closest work in the RL space is a 2024 arXiv paper on fair and firm real-time DNN scheduling (arXiv 2403.00766), which includes per-tenant SLO satisfaction as an explicit reward component and achieves 87% tenant compliance versus 60% for SLO-unaware RL baselines. In the non-RL space, a 2025 GPU cluster scheduling paper (arXiv 2512.10980) uses an aging-based fairness score in a hybrid priority scheduler, defining aging as "gradually increasing the effective priority of processes that have been waiting" — exactly the mechanism the target project encodes in its reward function, but implemented as a hand-engineered heuristic rather than a learned RL policy ([Source](https://arxiv.org/pdf/2512.10980)). The academic literature on OS scheduling aging (going back to Dijkstra) establishes that pure priority scheduling causes starvation, and aging is the classical remedy — but no RL paper has formalized aging as a **learned reward signal** for CPU process scheduling. The target project's "soft priority + aging reward" — where reward is shaped by both process priority and accumulated wait time, with priority weight increasing as wait time grows — appears to be a novel RL formalization of a classical OS mechanism.

Among RL schedulers that claim fairness, most treat it as a secondary analysis metric rather than a primary training objective. RLScheduler explores fairness post-hoc but does not include it in the reward ([Source](https://ar5iv.labs.arxiv.org/html/1910.08925)). The OSDI 2020 heterogeneity-aware scheduling work (Narayanan et al.) handles fairness through weighted fair sharing within a traditional optimizer, not RL, confirming that the community generally treats fairness as a constraint to be managed heuristically rather than a signal to be learned ([Source](https://www.usenix.org/system/files/osdi20-narayanan_deepak.pdf)).

## Conclusion

The literature confirms that the combination of **MaskablePPO + GraphSAGE + soft priority-aging reward + variable process counts + 500-seed statistical evaluation** for CPU process scheduling is not found in any existing paper. The three relevant subfields — OS parameter tuning (STUN, TuneAgent), cluster/cloud job scheduling (Decima, DeepRM, RLScheduler, MARL-GNN), and manufacturing job-shop scheduling (L2D, Geometric DAG, JSSP-GNN survey) — each contribute partial ingredients but none assembles them at the CPU process level. Decima provides the closest GNN+RL precedent but operates on Spark DAGs, not OS processes; Lassoued 2026 provides the closest MaskablePPO scheduling application but in job-shop manufacturing with no GNN; Huang & Ontañón 2022 provides the theoretical grounding for action masking; and the HPS aging paper (2025) provides the closest analog to priority aging, as a non-RL heuristic.

The most significant implication of this gap analysis is that evaluation rigor is also an underexplored differentiator. The highest-rigor action-masking scheduler paper uses 100 evaluation runs; trace-based cluster schedulers (Decima, GNN-RL HPC) evaluate on single real workload traces. **500 seeded synthetic workloads with controlled process-count variation** enables statistical claims about generalization that no found paper makes for CPU process scheduling. This positions the project's methodology as a contribution not only in algorithm design but in evaluation practice for learned schedulers.
